## 1. 引言

### 1.1 目的
定义在线购物系统的功能边界与业务规则，作为设计、开发、测试与验收的统一依据。
> **v1.5 修订**：原「单卖家在线购物系统**基线版本**」限定语删除——迭代 2 起系统已从单商品基线扩展为多商品、多客户版本。

### 1.2 范围

**迭代 1（基线，已交付）**：
**做**：单卖家商品发布与管理、买家免注册排队购买意向、口令码自助服务、交易冻结与结果标记、历史档案。
**不做**（需求方当时明确排除）：注册/登录（买家侧）、线上支付、物流、购物车、搜索分类、评价、库存、买家订单历史、App/小程序。

> **v1.5 重大变更**：上段「不做」清单中的 **注册/登录、搜索分类、库存、买家订单历史** 四项，已由挑战需求 A 转为 **做**。基线排除条款仅对迭代 1 有效，**不再是当前范围**。现行范围见第 8 章 8.1。

## 4. 业务规则（状态机）

> ⛔ **本轮次提示**：4.1~4.3 为**迭代 1 基线**状态机，其中「口令码」相关内容已随 C6 裁决全部失效。**v1.5 的有效状态机见 4.4**（完整图与转移条件由王振涛在 W-1 任务中绘制，见 [[业务流程图]]）。

### 4.1 商品状态机（迭代 1 基线，已被 4.4 取代）
`在售 →（手动冻结）→ 已冻结[manual] →（解冻）→ 在售`
`在售 →（队首**自动**进入交易，同时自动冻结）→ 已冻结[auto] →（标记成功）→ 已下架`
`已冻结[auto] →（标记失败且队列空）→ 在售`
`在售 / 已冻结[manual] →（手动下架）→ 已下架`
- 同一时间最多一件商品处于在售/冻结
- **队首进入交易与冻结均由系统自动完成**，卖家后台无"进入交易"操作（2026-10-07 拍板；后台手动仅"标记交易结果"与"冻结/解冻"两项）
- 手动下架**不因有排队意向而禁止**；下架后排队意向口令码全部失效
- 冻结期间不接收新意向；无超时自动解冻
- 买家端对手动冻结与交易冻结**不区分**文案
- **「进入交易」的触发机制**（2026-10-13 增补，回应第 1 次评审技术意见 #1「自动要写清什么条件触发」）：
  - 触发者：**系统**（`TradeService.enterDeal`），取队列首位，**卖家不可挑人**；
  - 触发条件：商品处于**在售**状态，且该商品存在「排队中」的意向；
  - 触发动作：队首意向置「交易中」，商品置「已冻结」、`frozenBy='auto'`、`frozenAt=当前时间`——**冻结由系统自动完成，卖家无需另行操作**；
  - 自动递补：交易失败后若队列仍有排队意向，下一位**由系统自动递补**进入交易、商品保持冻结，卖家无需再次操作；
  - **口径裁定（Q6，见 [[需求问题库]] #10；2026-10-13 本组决定不再向需求方追问）**：需求方第 8 条答复要求「买家提交意向后队首自动进入交易」。若照字面实现（提交即冻结），因 FR-B1 / FR-B2 规定「商品交易中不接收新意向」，第二位及之后的买家将无法提交，排队队列无法形成——这与"排队本身是本项目核心功能"相冲突。**处理方式**：保留队首由系统进入交易的机制（`TradeService.enterDeal`），买家可正常排队，队首进入交易时才冻结商品；由此产生的差异作为本组既定口径记录在此。若需求方后续主动提出调整，再按其答复对齐代码与文档。

### 4.2 意向状态机
`排队中 →（进入交易）→ 交易中 →（标记结果）→ 成功 / 失败`
`排队中 / 交易中 →（买家撤销）→ 已撤销`（交易中撤销：交易终止、后续队列递补；队列空则商品自动恢复在售）
终态三档：**成功 / 撤销 / 失败**；口令码随终态失效（重新排队除外，见 4.3）。

> **2026-10-13 代码对齐记录（FR-B5）**：原实现为「交易中拒绝撤销」（`IntentService.cancel` 抛「你已进入交易，无法自行撤销」），与 FR-B5 拍板口径矛盾。现已改为：交易中撤销 → `TradeService.abortDealByBuyer` 置该意向为已撤销并终止交易 → 队列有人则下一位自动递补（商品保持冻结）、队列无人则商品恢复在售；口令码随终态失效。补测试用例 17（交易中撤销且递补）、18（交易中撤销且队列空恢复在售），`mvn test` 18 组全通过。

- 排队按提交时间先到先得；冻结发生在进入交易时 → **v1.5 保留**（A.2.3-9 重申严格 FIFO）
- ~~口令码全局唯一、仅显示一次、不可找回~~ → **废止**（C6）
- ~~失效条件：交易结束（成功/失败）、意向撤销、商品下架~~ → **废止**（无口令码）

**商品状态机 —— 4 态**

| 从 | 到 | 触发条件（老师第 1 次点评技术意见 1、3、5：必须写清触发条件） |
| --- | --- | --- |
| 在售 | 已冻结[auto] | 存在「排队中」意向且商品在售 → 队首**自动**进入交易，交易服务在同一事务内改状态 |
| 在售 | 已冻结[manual] | 卖家手动冻结 |
| 已冻结[manual] | 在售 | 卖家手动解冻 |

**意向状态机 —— 6 个状态值，买家侧展示 5 类**

| 状态值 | 买家历史展示 | 说明 |
| --- | --- | --- |
| `QUEUED` | **待交易** | 排队中 |

### 8.5 需求空白衍生的风险（必须向客户书面告知）

- **R-A 队首阻塞链（最高优先级）**：买家提交意向 → 看不到位次不知何时轮到 → 轮到队首时卖家按电话联系不上 → 买家不能主动退出 → 卖家只能走「进入交易 → 标记失败」强行清退 → 清退期间商品被冻结、阻塞后续所有人。
  **需求方既不允许卖家在排队阶段清退意向（A.2.4-4 不采纳），又不允许跳过队首挑人（A.2.3-9）**，二者叠加意味着：队列里若有 N 条无效意向，就要走 N 遍完整的交易生命周期。本组已书面提示，需求方未采纳缓解建议。**评审时须逐条回应。**
- **R-B 队列永久污染**：无取消 + 无去重，恶意或误操作提交的意向永久占用队列，只能靠卖家逐条标记失败；叠加多商品 + 库存机制后影响面放大。
- **R-C 账号不可恢复且不可清理**：忘密码 / 电话填错 → 账号不可用；无注销 → 永久滞留；商家仍可见其完整手机号且不脱敏。
- **R-D 买家「黑盒」体验**：下单后看不到位次、看不到进展、收不到任何通知，只能被动等待线下联系。
- **R-E 无真实身份的线下交易风险**：卖家仅掌握用户名 + 电话，缺失真实姓名，售后与纠纷场景缺依据。

**本组自行实现的低成本缓解**（需求未涉及，见附三）：注册时手机号二次确认输入；下单页回显当前联系电话；提交意向时弹窗告知「提交后无法自助取消、无法查看排队进度」。

### 8.6 旧数据切换方案（需求方指定：B 方案 只读归档）

需求方从本组提交的三个方案中**指定 B 方案**（A.2.4-3）：旧系统（口令码时代）正在售卖的商品、排队中的意向、已有历史档案，**只读归档**——卖家后台可查，**不挂到新账号下，不迁移，不复活旧队列**。

实施细节：由 `config/MigrationRunner` 在检测到旧数据时自动执行一次——
1. 建立「未分类 / 历史商品」两级归档类别；
2. 商品补 `stock=1`、挂到历史商品类别；在售与冻结状态统一转「已下架」（`offShelfReason=MANUAL`）；
3. 旧单图字段迁移为 `ProductImage` 第一条（即主图）；
4. 旧意向全部置 `ARCHIVED`，`buyerId` 保持 `null`；口令码原值保留备查。

**验收口径**：旧商品与旧意向在卖家后台历史里可查，**不能进入新队列、不能被交易、不关联任何账号**。
